# git-rebase

## 対象の確認

1. 現在のブランチ、作業ツリー、upstream、リモートを確認してfetchし、`git log --oneline --graph` で対象のコミット列を読む。未コミット変更があれば保持して止め、自動でstashやcommitしない。
2. upstreamだけでなく `git branch -r --contains <commit>` などでも対象が公開済みか確認する。公開済みのコミットを書き換える必要がある場合は、影響とpush方法を説明し、ユーザーがその書き換えまで依頼・承認していることを確かめる。未公開であることを確認できない場合は、未公開と決めつけない。
3. 残すコミット、まとめる範囲、順序を確定する。「3つ目以降」などの順序は確認した対象範囲を基準にし、範囲が曖昧なら確認する。リポジトリの最初のコミットから全履歴を自動で対象にしない。

## 実行と確認

実行前のHEADを記録し、対象直前のコミットを基点に `git rebase -i <base>` を使う。利用可能なシーケンスエディタでtodoを用意し、指定範囲の `pick`、`fixup`、`squash` を設定する。mergeコミットが含まれる場合は構造を確認し、意図せず履歴を平坦化しない。

競合が起きたら停止状態と対象ファイルを確認する。解決できる範囲で修正し、`git add -- <path>`、`git rebase --continue` で続ける。解決方針が分からなければユーザーに確認する。中止が必要な場合は `git rebase --abort` を使う。

コミット整理だけの依頼では、実行前のHEADと完了後のHEADのファイル内容が一致することを `git diff <before-head> HEAD` で確認する。`git log --oneline` と `git status --short` も確認し、変更したコミット列と残った作業を報告する。pushは依頼に含まれる場合のみ行い、公開済み履歴への無条件のforce pushは行わない。
